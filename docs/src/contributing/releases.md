# Releases

## Versioning

rudof follows [Semantic Versioning](https://semver.org/) with the caveat that, while the version
is below `1.0.0`, breaking changes can appear in a minor version. All crates in the workspace share
one version, and every dependency is version-aligned: a crate published as `0.3.25` depends on
`0.3.25` of its siblings.

## Milestones and releases

A milestone is the contents of a release, named exactly as the version it will ship as. It is what
turns a set of merged pull requests into a published version; publishing the release is what closes
the issues it contains — see [Issue policy](./issues.md#lifecycle-and-closing).

There is no perpetual milestone: if an issue is not committed to a specific version, it has no
milestone and stays in the backlog.

## The changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/). It is written by hand and
it is not the same thing as the GitHub release notes:

- **The changelog** explains, for a user, what changed and what they have to do about it. Entries
  are written by **the author of the pull request**, under `## [Unreleased]`, in the same pull
  request as the change. Reviewers check it is there.
- **The release notes** are generated by GitHub from the titles of the merged pull requests, which
  is why those titles follow a convention.

Use the Keep a Changelog sections (`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`,
`Security`) and write for someone who does not have the pull request open.

Internal changes with no user-visible effect do not need a changelog entry.

## Publishing a release

Releases are cut by maintainers with release rights (see
[`GOVERNANCE.md`](https://github.com/rudof-project/rudof/blob/master/GOVERNANCE.md)).

1. **Check the milestone.** Every issue in it is either closed or carries
   `status/pending-release`. Anything still open and unmerged moves to the next milestone.
2. **Cut the changelog.** In a pull request, rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`
   and open a fresh empty `## [Unreleased]` above it. Merge it before releasing.
3. **Run the `Release` workflow** from the Actions tab on `master`, choosing `patch`, `minor` or
   `major`, and `prerelease` for a release candidate. It bumps the workspace version and the
   internal dependencies, updates `nix/packages.nix` and the version pinned by the online demo,
   commits as `chore: release X.Y.Z [skip ci]`, and creates the GitHub release with generated
   notes.
4. **Check the downstream workflows.** Publishing the release triggers `publish.yml` (crates.io),
   `npm.yml` (the `@rudof/rudof` package) and `artifacts.yml` (binaries). All three must succeed
   before the release is announced.
5. **Close the milestone.** Publishing the release already closed its issues and dropped their
   `status/pending-release`; closing the milestone records that the version is done.
6. **Create the next milestone** for the version that follows.

For a release candidate, stop after step 4: the milestone stays open, and the issues stay in
`status/pending-release` until the stable release ships.

## What is released from where

| Artifact | Workflow | Trigger |
| --- | --- | --- |
| GitHub release and tag | `release.yml` | Manual |
| crates.io packages | `publish.yml` | A published release |
| `@rudof/rudof` on npm | `npm.yml` | A published release (release candidates get the `next` tag) |
| Binaries for Linux, macOS, Windows and Docker | `artifacts.yml` | A published release |
| The manual | `gh-pages.yml` | Pushes to `master` touching `docs/`, and after `npm.yml` |

Only the latest published version is supported. Fixes are not backported: they ship in the next
release.
